Engineering overview

For contributors and technical readers. Parents: back to the main site.

Architecture

t@sk4ce runs on a Linux computer in your home and works with any router. Here's the system layout:

Key loops:

  • Lock loop (backend, every 30 seconds): Decides which devices should be blocked based on chore completion, time windows, and overrides. Pushes the blocked MAC list to the blocker.
  • Reconcile (blocker, continuous): Pulls the blocked MAC list from the backend and applies ARP/NDP redirects and firewall rules. Sends device discoveries and resistance signals back.
  • Heartbeat: The blocker calls the backend every 30 seconds. If the backend doesn't hear from the blocker for 90 seconds, the app shows a "box offline" banner.

Enforcement model and limits

The blocker redirects a blocked device's traffic using ARP (IPv4) and NDP (IPv6), then drops internet-bound packets with nftables and serves a captive portal. It fails open: if the box dies, devices return online.

What it does

  • Blocks/unblocks devices in seconds, based on real-time policy decisions.
  • Watches for devices trying to work around it (hotspots, changing network settings) and flags them as "resisting."
  • Works with IPv4 and IPv6.

What it doesn't do

  • Block cellular hotspots or devices not on your home network.
  • Defeat routers with ARP inspection or client isolation (rare, but they exist).
  • Stop a determined kid with another device, a laptop on a different network, or a hotspot from a friend.
  • Prevent the box itself from being turned off or unplugged.

See router compatibility list and technical comparison with other options.

Data model

All data is stored in SQLite on your home box, with foreign keys and CHECK constraints to enforce integrity.

Core tables

  • chores, chore_steps: The chore library (reusable templates).
  • chore_assignments, assignment_kids: Who gets which chore and when (daily, weekly, once; individual, race, or team).
  • chore_runs, run_kids, run_step_ticks: Today's work. Runs read the chore title, points, and steps live at render time.
  • chore_photos, threads, thread_messages: Photos as proof, plus chore threads, private kid threads, and a family chat.
  • points, redemptions: The economy ledger. Signed amounts for chores, bonuses, team shares, and redemptions.
  • badge_awards, custom_badges, kid_flair: Progression. Levels, streaks, and unlockable items are derived from the ledger, not stored.
  • devices, device_groups, time_windows, overrides: Network policy. Allowed/free hours, manual locks/unlocks.
  • users, family_settings: Parents, kids, and family config (reset time, screen time price, blocker status).

Security notes

Auth and secrets

JWT bearer tokens for parents and kids. Passwords hashed with bcrypt. Secrets (SECRET_KEY, JWT_SECRET_KEY, INTERNAL_TOKEN) are generated on first boot and stored in DATA_DIR/secrets.json (mode 0600), overridable by env.

Kid login

Kids sign in by device IP: the app matches the request IP to a known device and asks for a PIN (if set). Failed tries are rate-limited. IPs come from X-Real-IP only when trusted (the frontend's static address in Docker Compose).

Photos

Stored on your box with one-way hashes. Parents can view them; kids can't delete them (parents approve chores, so they decide if a photo counts as proof).

Network

The blocker runs with NET_ADMIN and NET_RAW capabilities (host networking). The internal INTERNAL_TOKEN is shared between backend and blocker; they use it for the API calls that control blocking.

Testing

Unit tests

Backend: pytest. Frontend: jest. Blocker: pytest. Run with cd backend && python -m pytest, etc.

Lab

An isolated Docker network with a fake router, fake internet, real backend and blocker, and simulated kid devices. Tests real ARP, nftables, and captive portal journeys. See lab/README.md.

Browser e2e

Playwright tests in the lab. Run with bash scripts/lab.sh e2e.

CI

GitHub Actions runs linting, all unit tests, lab e2e, and a security scan before each push. Keep the checks green.

How to add a badge or flair item

Badges and flair are defined in the codebase and unlock at certain milestones (level, chore count, streak, etc.).

Built-in badges

Edit backend/app/models/badges.py. Add a new entry with a key, name, icon emoji, and unlock condition. The unlock logic lives in backend/app/badges/.

Custom flair items

Edit backend/app/models/flair.py. Add a slot, name, and item variants (names, colors, rings). Parents unlock flair by spending points or reaching milestones.

See the full data model and examples.
